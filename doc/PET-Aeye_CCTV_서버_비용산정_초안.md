> **v0.2**: 기준안을 **NPU 혼합형**(실내 전 구역 자체 NPU 카메라 · 실외만 시중 CCTV + 엣지 박스)으로 변경. v0.1 서버형(일반 CCTV + GPU 서버)은 비교안으로 유지(§3.2).  
> **v0.3**: 실내 NPU 카메라를 **Wi-Fi 연결**(홈캠과 같은 Wi-Fi형)로 변경 · **관제실 최소화** 후 횡성 펫 리조트 개관 시 **횡성 통합 관제실로 이전**(§4.5).

> 단위: **만원 · VAT 별도**. 단가는 국내 B2B 시장 참고 수준의 **가정치**이며, 현장 실측과 견적 3곳 이상으로 확정합니다.  
> 바이탈(FMCW) 센서는 자체 기술 PoC 범위라 이 산정에서 제외합니다(§7).

- microSD: 하루 약 8.6GB(스마트 녹화) → 128GB를 약 15일마다 덮어써 5년간 약 120회입니다. 일반 카드(약 1.5만원)는 연속 쓰기 보증이 없어 1~2년 안에 고장 날 수 있으므로 **고내구성 등급**(Samsung PRO Endurance급 · 대량 구매 약 2.5만원)으로 잡았습니다. 이 등급이면 5년간 교체 없이 쓰고, 고장분은 교체 적립(§5)에서 처리합니다.

- Wi-Fi 용량: 스마트 녹화(§4.2)로 평균 150대 × 0.8Mbps ≈ 120Mbps, 모든 카메라가 동시에 활동해도 최대 약 300Mbps입니다. Wi-Fi 6 AP 14대(카메라 전용)면 AP당 최대 약 20Mbps라 여유가 있습니다. 콘크리트 벽을 고려해 복도 천장에 객실 8~12개당 1대씩 배치하고, 설치 전 신호를 측정합니다.
- 끊김 대비: 카메라가 microSD에 먼저 녹화하고 연결이 돌아오면 서버로 다시 보냅니다. 이상행동 감지는 카메라 안에서 돌아 Wi-Fi가 끊겨도 계속되고, 알림은 연결 복구 즉시 올라옵니다.
- **정전 대비 (UPS 최소화):** Wi-Fi로 연결한 카메라는 건물 콘센트 전원이라 정전되면 어차피 꺼집니다. 그래서 층별 UPS(240)는 두지 않고, **서버 랙 UPS 1대**만 둡니다. 목적은 두 가지입니다.
  - 서버 · 녹화 스토리지 · NAS를 **안전하게 종료**(5~10분)해 녹화 파일 · DB · RAID 손상을 막습니다. 네트워크 관리 카드가 정전을 감지해 자동 종료합니다.
  - 코어 스위치 · 방화벽 · **LTE 백업 라우터**를 살려 두어, 정전 · 회선 장애를 **스태프 앱 · 문자로 즉시 알립니다.** 정전 때는 냉난방도 멈추므로 화면 감시보다 즉시 알림과 현장 출동이 반려견 안전에 더 중요합니다.
  - 전원이 돌아오면 카메라는 자동으로 재접속하고, microSD에 남은 정전 직전 구간을 서버로 다시 보냅니다.

#### 3.1.1 현장 상태별 경우 (통합형 카메라 · 관제 최소 · 3단 저장 공통)

| 현장 상태 (D0–10 실측) | 연결 | 합계 |
|------------------------|------|------|
| 기존 아날로그 CCTV (동축 + 12V 전원선) | **Wi-Fi + 기존 전원선 재사용 (기준)** | **약 0.80억** |
| 기존 CCTV 랜선(UTP)이 객실까지 있음 | PoE + 기존 UTP 재사용 (점검 · 커넥터 대당 3 · PoE 스위치 8대) | 약 0.79억 |
| 카메라 배선 · 전원 모두 없음 | Wi-Fi + 천장 콘센트 신설 (150곳 × 6) | 약 0.89억 |
| (참고) PoE 신규 배선 | 156대 × 15 신규 배선 | 약 1.00억 |

- PoE로 연결하는 경우 층별 PoE 스위치에 소형 UPS를 달면 정전 중에도 카메라가 동작합니다(층별 4대 약 +260, 예비비 포함). 기준안에는 넣지 않았습니다.

- 통합형이라 구역마다 연결 방식을 섞어도 같은 카메라를 씁니다(예: 본관 Wi-Fi · 별관 기존 UTP로 PoE).

- 기존 UTP가 있으면 유선이 가장 싸고 안정적입니다. 없으면 Wi-Fi가 신규 배선보다 약 1,000~2,000만원 적습니다.

공통 사항 (v0.4 · v0.2):

- GPU 서버가 빠지는 이유: 실내 150대는 카메라가 직접 분석하고, 실외 6대만 엣지 박스(16~32채널 처리)가 맡습니다. 카메라를 넘나드는 추적 · 혼잡도 같은 집계는 결과값만 모으므로 앱 · DB 서버 CPU로 충분합니다.
- 연속 녹화 30일은 유지하되, v0.4는 스마트 녹화 · 3단 저장으로 스토리지 비용을 줄였습니다(§4.2). v0.2는 2Mbps 연속 녹화 기준입니다.
- NPU 통합형 단가 범위: 약 9.6만원(1,000대 이상) ~ 12만원(500대 미만). 12만원이면 v0.4 합계 약 0.82억입니다.
- 기존 카메라 재사용(§3.3)은 이 안에서는 **실외 · 보안 전용 카메라**에만 적용됩니다. 객실 · 공용 분석은 NPU 카메라로 새로 답니다.

## 4. 서버 사양 산정 근거

### 4.1 구성 원칙 — 온프레미스 + 클라우드 혼합

| 위치 | 담당 | 이유 |
|------|------|------|
| **온프레미스 (관제실)** | 영상 수집 · 녹화 · AI 검출(실외) · 관제 웹 | 156대 상시 영상(v0.4 약 132Mbps · v0.1 약 312Mbps)을 클라우드로 올리면 회선 · 저장 비용이 커지고, 회선 장애 시 관제가 멈춥니다. |
| **클라우드** | 보호자 앱 · API · 라이브 중계 · 리포트 · 푸시 · 백업 | 외부 접속은 보호자 배정 객실만, 필요한 만큼만 중계합니다. 관제실 서버를 외부에 직접 노출하지 않습니다. |

참고로 클라우드 녹화형 CCTV 서비스는 카메라당 월 1~2만원 수준이라, 156대면 월 약 160~310만원이 회선비와 별도로 듭니다. v0.4 기준안의 녹화 스토리지(650만원)는 그 사용료 약 2~4개월분입니다.

### 4.2 녹화 스토리지

#### v0.4 기준 — 스마트 녹화 + 3단 저장 (총 30일)

**스마트 녹화:** NPU 카메라가 움직임 · 이벤트를 직접 판단해 **활동이 있을 때만 고화질(약 2Mbps)**, 조용할 때(야간 수면 · 빈 객실)는 **저화질 · 저프레임(약 0.3Mbps)** 으로 녹화합니다. 활동 시간 30%를 가정하면 평균 약 0.8Mbps로, 2Mbps 연속 녹화 대비 **약 60%** 줄어듭니다.

| 가정 | 값 |
|------|------|
| 평균 비트레이트 | NPU 150대 × 약 0.8Mbps + 실외 시중 6대 × 2Mbps ≈ **약 132Mbps** |
| 일 저장량 | **약 1.4TB / 일** (v0.1 대비 약 40%) |
| 총 보존 기간 | **연속 녹화 30일** · 이벤트 클립 90일 · 분쟁 · 사고 건은 지정 시 별도 영구 보관 |

| 단계 | 위치 | 보관 | 용량 | 비용 |
|------|------|------|------|------|
| **1단 · 카메라** | 고내구성 microSD 128GB × 150 | 최근 약 14일 | 대당 128GB | **375** (A 항목에 포함) |
| **2단 · 핫** | 앱 · DB 서버 내장 HDD 8TB × 2 (미러) | 최근 **3일** · 관제 화면 즉시 재생 | 약 8TB | **150** |
| **3단 · 콜드** | 8베이 NAS · 8TB HDD × 8 · RAID6 · 유휴 시 디스크 정지 | 4~30일 연속 녹화 + 이벤트 클립 90일 | 실사용 약 48TB (필요 약 45TB) | **500** |
| **합계** | | | | **1,025** (서버 쪽 650 · v0.1 1,150 대비 서버 쪽 −500) |

- 1단(microSD)까지 합친 저장 비용은 1,025만원으로 v0.1(1,150)과 큰 차이가 없습니다. 대신 **장애 대비 이중 저장**(카메라 + 서버)이 생기고 Wi-Fi 부하가 줄어듭니다. 저장비만 줄이려면 microSD를 32GB(약 4일 · 대당 약 1만원)로 낮출 수 있습니다(−225).

- **운영:** 매일 새벽 2단 → 3단으로 일괄 이동하고, 30일이 지나면 자동 삭제합니다. 콜드도 온라인 HDD라 테이프와 달리 몇 분 안에 찾아 재생할 수 있습니다.
- **카메라 microSD가 1단 역할:** 서버 · Wi-Fi 장애 때도 최근 약 14일이 카메라에 남아, 연결 복구 후 빠진 구간을 채웁니다.
- **테이프(LTO) 검토 결과:** 드라이브 약 800만원이 고정비라 30일 보관(약 45TB)에서는 HDD보다 비쌉니다(테이프 약 1,020 · HDD 약 650). 보관 기간을 **1년 이상**으로 늘릴 때(약 490TB · 테이프 약 1,490 · HDD 약 4,000)부터 테이프가 유리하므로 그때 3단 뒤에 4단으로 붙입니다.
- **개인정보:** 보관 기간을 짧게 두고 자동 삭제하는 것이 영상정보 처리 원칙에도 맞습니다. 보관 기간 · 삭제 방식은 객실 안내문과 운영방침에 적습니다.

#### v0.1 · v0.2 기준 — 2Mbps 연속 녹화 (참고)

| 가정 | 값 |
|------|------|
| 평균 비트레이트 | 4MP · H.265 · 15fps · 스마트 코덱 · 정적 장면 위주 → **대당 약 2Mbps** |
| 전체 유입 | 156대 × 2Mbps = **약 312Mbps** |
| 일 저장량 | 약 3.4TB / 일 |
| 보존 기간 | **연속 녹화 30일** (분쟁 · 보안 대응) · 이벤트 클립은 별도 장기 보관 |
| 필요 용량 | 약 101TB |
| 구성 (기준) | 2U 12베이 서버 + 16TB 엔터프라이즈 HDD 12개 · RAID6 → **실사용 약 160TB** (여유 약 50%) |

보존 기간을 14일로 줄이면 필요 용량은 약 47TB로 줄어, 하한 구성(약 900만원)으로 충분합니다.

### 4.3 AI 분석 위치

**NPU형 (v0.2 · v0.3 공통)**

| 가정 | 값 |
|------|------|
| 실내 150대 | 카메라 안 NPU에서 탐지 · 포즈 · 추적 (YOLO11n 기준 640 입력 초당 약 100프레임 · 실제 운용 5~10fps라 여유) |

| 모델 배포 | 같은 모델을 NPU 형식(`.axmodel`)으로 변환해 **펌웨어 OTA 에이전트**로 단계 배포(§4.3.1). 칩이 알아서 배포하지는 않음 |

#### 4.3.1 NPU 모델 · 펌웨어 OTA 배포

칩(AX630C)이나 개발보드(MaixCAM2)가 출고만으로 최신 모델을 받는 구조는 **아닙니다.** 양산 펌웨어에 **OTA 에이전트**(서명 검증 · 다운로드 · 적용 · 보고)를 넣고, 서버에서 버전을 밀어 줄 때 자동 배포가 됩니다. 홈서비스 · 횡성 리조트와 **같은 제품 · 같은 OTA**를 씁니다.

| 구분 | 내용 | 주기 |
|------|------|------|
| 펌웨어 OTA | OS · 카메라 앱 · OTA 에이전트 · RTSP · 인증 · 네트워크 | 드묾 (분기~반기 · 보안 패치 시) |
| AI 모델 OTA | 탐지 · 포즈용 `.axmodel` + 설정(`.mud` 등) | 잦음 (현장 데이터 모이면 수주~수개월) |

- **모델만 바꿀 때**는 펌웨어 전체를 다시 깔지 않습니다. 파일 용량이 작고 위험도 낮습니다.
- **시설마다 다른 모델을 두지 않습니다.** 한 화면의 여러 마리를 한 모델이 처리하므로 영종 · 횡성 · 홈서비스에 같은 모델을 배포하고, 객실 · 공용 · 집은 **임계값 · ROI(관심 영역) 설정**만 다르게 둡니다.

**배포 흐름**

1. 학습 (횡성 GPU — **평소 사내 LLM**, 재학습은 가끔 · 또는 클라우드) → ONNX 내보내기  
2. Pulsar2 등으로 NPU용 `.axmodel` 변환 (MaixCAM2 계열 타깃 `AX620E` · 양산 칩 확정 후 타깃 고정)  
3. OTA 서버에 버전 등록 — 서명 · 해시 · 최소 펌웨어 버전 · 릴리스 노트  
4. **카나리:** 영종 5~10대(또는 횡성 한 층)만 배포 → 오탐 · 누락 · 재시작 · 메모리 확인  
5. 층 · 시설 · 전 대 순으로 확대 (홈서비스는 구독 기기 단계 롤아웃)  
6. 카메라가 **유휴 시각**(야간 · 빈 객실 · 집이면 보호자 미시청)에 받아 적용 → 버전 · 헬스체크를 서버에 보고  
7. 이상 시 **이전 모델로 자동 롤백** · 관제에 실패 대수 알림  

**인프라 (부담)**

| 위치 | 역할 |
|------|------|
| 영종 개관~횡성 개관 | 클라우드 OTA (홈서비스와 공용) 또는 영종 앱 서버에 OTA 메타 · 패키지 보관 |
| 횡성 개관 후 | 횡성 온프레미스(랙 4~6 · GPU는 사내 LLM·가끔 재학습)가 **호텔 · 리조트 기기**의 주 OTA 서버. 홈캠은 클라우드 OTA 유지(가정 회선) |
| 카메라 | 주기적으로 OTA 서버에 버전 조회(폴링) · 서명된 패키지만 설치 · 실패 시 롤백 |

**개발 · PoC 단계 (MaixCAM2)**  
USB · microSD 이미지 굽기 또는 SSH/SFTP로 `/root/models`에 파일을 넣는 수동 배포입니다. 양산 ODM 때 OTA 에이전트를 펌웨어 P0로 넣습니다(`PET-Aeye_홈서비스_기획_초안.md` §3.2 · §4.5).

**보안**  
기기별 고유 인증서 · **서명된 펌웨어 · 모델만** 설치 · 카메라에 SSH를 운영망에 상시 열어 두지 않음 · OTA 실패·롤백 로그를 관제에서 확인.

**서버형 (v0.1 · 비교)**

| 가정 | 값 |
|------|------|

### 4.4 앱 · DB 서버

관제 API · WebSocket · Redis · PostgreSQL을 관제실 서버 1대에 두고, 매일 백업 NAS와 클라우드로 백업합니다.

### 4.5 관제 운영 단계 — 영종 최소 → 횡성 통합

| 단계 | 시기 | 구성 |
|------|------|------|
| **1단계 · 영종 현장 최소 관제** | 영종 개관 ~ 횡성 개관 | 프런트 · 사무실에 모니터 2면 + 관제 PC 1대. 관제 화면은 웹(React)이라 사무실 PC · 태블릿 어디서나 접속. 야간 근무자는 **스태프 앱 알림**으로 대응 (상시 화면 감시 대신 이벤트 중심). |
| **2단계 · 횡성 통합 관제** | 횡성 펫 리조트 개관 시 | 횡성 통합 관제실(비디오월 · 콘솔 · 관제 PC)에서 영종을 **원격 관제**. 영종 모니터 · PC는 현장 확인용으로 계속 사용(매몰비 없음). |

- **영종에 남는 장비:** 녹화 스토리지 · 엣지 박스 · 앱 · DB 서버 · 백업 NAS. 영상 원본은 영종에 두고, 횡성에는 **결과값 · 이벤트 클립 · 필요할 때만 라이브**가 갑니다. 회선 장애가 나도 영종 현장은 단독으로 동작합니다.
- **회선:** 동시 라이브 10채널 × 2Mbps ≈ 20Mbps 상행이면 충분해 기존 기업용 회선(§5)으로 처리합니다. 연결은 사이트 간 VPN으로 하고 관제 서버를 외부에 직접 노출하지 않습니다.
- **이전 비용:** 통합 관제실 구축비는 횡성 문서(`PET-Aeye_횡성펫리조트_카메라_구성_초안.md` §5.1 G)에 넣었습니다. 영종 쪽 추가 비용은 VPN 장비 설정 수준(방화벽 300에 포함)입니다.
- **현장 인력:** 영종 야간 근무자는 관제 전담이 아니라 돌봄 인력이 알림에 대응하는 방식입니다. 관제 전담 인력은 2단계부터 횡성에서 두 시설을 함께 봅니다.

- NPU 카메라 수명은 5년으로 보고 교체 적립(§5)에 고장 교체만 넣었습니다.
- 외부 SaaS 판매(§5.4) 시에도 같은 구조로 "객실(카메라)당 월 구독" 원가 기준이 됩니다. 외부 고객은 대개 기존 카메라를 재사용하므로 구축비는 서버 · 네트워크 위주로 줄어듭니다.
